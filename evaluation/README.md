# Evaluation

## Purpose

This directory contains the repeatable evaluation framework for the SAP GenAI Incident Assistant.

The goal is to evaluate the assistant against predefined expected behavior instead of judging responses only by visual inspection.

## Files

```text
evaluation/
├── evaluate.py
├── metrics.py
├── dataset.json
└── README.md
```

### `dataset.json`

Contains the evaluation cases and expected behavior.

Each case defines:

- ticket and scenario category;
- expected status;
- expected SAP MM process;
- expected Human-in-the-Loop behavior;
- required evidence identifiers;
- required clarification concepts when applicable;
- forbidden claims used for deterministic hallucination checks.

### `metrics.py`

Implements deterministic metrics over structured assistant responses.

### `evaluate.py`

Loads the evaluation dataset and a JSON file containing application results, calculates the metrics, and writes a consolidated evaluation artifact.

## Metrics

### Classification Accuracy

Measures whether the assistant identifies the expected SAP process.

```text
Correct Process Classifications / Evaluated Cases
```

### Status Accuracy

Measures whether the workflow returns the expected control state, such as:

- `COMPLETED`;
- `NEEDS_CLARIFICATION`;
- `INSUFFICIENT_EVIDENCE`;
- `OUT_OF_SCOPE`;
- `HUMAN_VALIDATION_REQUIRED`.

### Grounded Answer Rate

Measures whether diagnostic answers are accompanied by expected evidence and whether cases without supporting evidence avoid unsupported causes.

### Citation Coverage

Measures coverage of required evidence identifiers.

```text
Required Evidence IDs Cited / Required Evidence IDs
```

### Hallucination Rate

Checks responses for explicitly forbidden claims defined in the dataset.

This is intentionally conservative and deterministic. It does not claim to detect every possible hallucination.

Lower is better.

### Clarification Accuracy

Measures whether scenarios with missing information request the required diagnostic concepts.

### Escalation Accuracy

Measures whether `human_validation_required` matches the expected result.

### Human Approval Compliance

Checks whether cases requiring human approval preserve the HITL boundary and avoid language indicating that a protected action was executed autonomously.

### Average Response Time

Calculates mean response time when `response_time_ms` is present in application results.

## Running the Evaluation

The evaluation consumes structured outputs generated by the application.

Example:

```bash
python evaluation/evaluate.py \
  --results evidence/test_results.json
```

The default output is:

```text
evidence/evaluation_results.json
```

A different destination can be supplied:

```bash
python evaluation/evaluate.py \
  --results evidence/test_results.json \
  --output evidence/evaluation_results_run_01.json
```

## Expected Application Result

A result may look like:

```json
{
  "ticket_id": "TKT-002",
  "status": "COMPLETED",
  "process": "Invoice Verification",
  "possible_causes": [
    "A price difference exists between the PO and invoice."
  ],
  "missing_information": [],
  "sources": [
    {
      "document_id": "KB-MM-005"
    },
    {
      "document_id": "KB-MM-006"
    }
  ],
  "human_validation_required": false,
  "response_time_ms": 1420
}
```

The results file may be either a JSON array or:

```json
{
  "results": []
}
```

## Evaluation Dataset Coverage

The initial dataset covers:

1. grounded Purchase Order release analysis;
2. grounded invoice price-variance analysis;
3. missing information;
4. insufficient evidence;
5. out-of-scope SAP request;
6. state-changing action requiring human approval;
7. authorization error;
8. conflicting evidence.

This directly exercises the challenge requirements around RAG, hallucination prevention, clarification, HITL, scope control, and exception handling.

## Interpretation

A strong POC should aim for:

- high classification accuracy;
- high status accuracy;
- high grounded-answer rate;
- high citation coverage;
- low hallucination rate;
- high clarification accuracy;
- high escalation accuracy;
- full human-approval compliance.

These metrics are evaluation signals for the defined test set. They are not production SLAs and do not establish general model accuracy.

## Important Limitation

The deterministic hallucination metric checks known forbidden statements and therefore cannot detect every unsupported claim.

A production evaluation strategy should combine:

- deterministic checks;
- larger labeled datasets;
- expert SAP review;
- regression testing;
- retrieval-quality evaluation;
- security and prompt-injection testing;
- periodic review of failure cases.

## Reproducibility

The dataset is version-controlled with the source code. Expected behavior should only change through an explicit review because changes affect regression results.

The LLM does not assign its own evaluation score. Evaluation is performed outside the model response by application logic.
